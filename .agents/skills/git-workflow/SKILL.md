# Git Workflow & Release

## Commit Scopes

- **Load [`references/commit-scopes.md`](references/commit-scopes.md)** when branching or committing changes to a userscript (`src/*.user.js`) to look up its canonical `<script-slug>`.
- **Skip `references/commit-scopes.md`** when committing infrastructure changes — use `tools`, `workflow`, `dist`, `docs`, `repo`, or `lib` directly.
- Isolate structural refactoring into dedicated `refactor(<scope>)` commits, separate from `fix` or `feat` changes.

## Versioning & GitHub CLI

- Bump `// @version` in the script header only at the start or end of work on a topic branch; keep intermediate commits at the same version.
- Manual bump commit: `chore(<script-slug>): bump version to x.y.z`. When releasing with `tools/workflow.py release`, version bumps fold automatically into the latest unpushed script commit via `--fixup` rebase.
- Use `gh` and `git` CLI tools for all GitHub operations (PRs, issues, releases, checks) instead of direct API calls or scraping.

## Release Execution

Treat `tools/workflow.py` as a **black-box CLI** during release workflows. Discover flags and behavior only through `--help`, `check --json`, and `--dry-run`.

```bash
# 1. Pre-flight: inspect unreleased scripts and cascading lib/ dependency bumps
python tools/workflow.py check --json

# 2. Simulate release without creating commits or modifying files
python tools/workflow.py release --dry-run --non-interactive

# 3. Release only specific script(s) when other unreleased scripts exist on `dev`
#    `--scripts` accepts comma-separated relative paths, canonical slugs (preferred),
#    1-based indices from `check --json`, `all`, or `none`.
python tools/workflow.py release --dry-run --non-interactive --scripts mb-release-day-week --bump-type patch
python tools/workflow.py release --non-interactive --push --scripts mb-release-day-week --bump-type patch

# 4. Validate @version headers, rebase onto main, and push to main (all scripts)
python tools/workflow.py release --non-interactive --push

# 5. Include accompanying non-script files (e.g. tests/test_*.js, docs) or release files only
python tools/workflow.py release --files <path1,path2|all> --non-interactive --push
# Add `--scripts none` if modified userscripts also exist on `dev` and should stay unreleased
```

- **Key `release` flags:** `--bump-type {patch,minor,major,none,auto}`, `--scripts <paths|slugs|indices|all|none>`, `--files <path1,path2|all>`, `--commit-type <type>` and `--commit-msg "<summary>"` (for uncommitted `src/*.user.js` changes), `--dry-run`, `--non-interactive`, `--push`.
- **Include tests and other docs when releasing a script:** By default, `workflow.py release` only copies the script files (`src/*.user.js`) and their `docs/descriptions/*.md` files to `main`, leaving tests (`tests/*`) and other docs behind on `dev`. If your dry-run lists accompanying test or doc files under *"remaining on 'dev'"*, commit them first and pass `--files <path1,path2>` (without `--scripts none`) so they go to `main` together.
- **How uncommitted changes work during a release:**
  - **Uncommitted `--files` targets:** Stops the release — commit or stash them first.
  - **Uncommitted `src/*.user.js` (and `docs/descriptions/*.md`):** Automatically staged and committed as part of the release.
  - **Staged changes in other files:** Shows a warning and asks whether to continue (auto-continues when using `--non-interactive`).
  - **Unstaged or untracked files on `dev`:** Left untouched via `--autostash` during rebase, **unless** a separate `main` worktree has uncommitted or untracked files (which stops the release).

Pushing to `main` triggers GitHub Actions to inline shared `lib/` dependencies and sync the `dist` branch (only when `src/**` or `lib/**` changed).

## NEVER Rules

- **NEVER read or inspect `tools/workflow.py` source code during a release workflow** — treat it as a black box. Use `--help`, `check --json`, and `--dry-run`. If the CLI fails unexpectedly or rejects flags, stop and report the exact command and error to the user instead of opening `tools/workflow.py`. (Only read `tools/workflow.py` when the user explicitly asks to debug or modify the tool itself.)
- **NEVER push directly to `main` or `dist` manually** — `tools/workflow.py release` validates `@version`, isolates selected paths (via `--scripts` / `--files`), rebases onto `main`, and GitHub Actions syncs `dist`; manual pushes bypass version checks and break CI-built artifacts.
- **NEVER edit files under `dist/`** — `dist/` is generated by `tools/build_dist.py` and CI from `src/*.user.js` and `lib/*.js`, so manual edits are overwritten on the next build.
- **NEVER bump `// @version` on intermediate topic-branch commits** — intermediate bumps fragment release history and interfere with `--fixup` squashing.
- **NEVER invent scopes outside [`references/commit-scopes.md`](references/commit-scopes.md)** (for userscripts) or `tools`, `workflow`, `dist`, `docs`, `repo`, `lib` — `tools/workflow.py` maps commits to scripts using exact slug matches.

## Common Rationalizations

| Rationalization | Reality / Required Action |
| :--- | :--- |
| "I'll quickly peek at `tools/workflow.py` to check how `--scripts` or uncommitted files work." | `tools/workflow.py` is a black box during releases. Use `--help`, `check --json`, and `--dry-run` only; never read its source unless asked to debug or modify the tool. |
| "The CLI printed an error on `--scripts`, so I should read `tools/workflow.py` to see why." | Read the CLI's error output and valid selector list (or `--help` / `check --json`), or report the CLI error to the user. Do not open `tools/workflow.py`. |
| "It's a one-line fix, I'll push straight to `main`." | Run `python tools/workflow.py release --dry-run` then `--non-interactive --push` (or `--files <path>` for non-script files) so checks and branch isolation run. |
| "I'll edit `dist/*.user.js` directly to test quickly." | Edit `src/*.user.js` or `lib/*.js` only; run `python tools/build_dist.py --out dist --script "<path>"` if you need a local `dist/` build. |
| "Every commit on my topic branch needs a new `@version`." | Bump `@version` only at the start or end of the topic branch, or let `workflow.py release` fold it. |
| "I'll abbreviate the script name as the scope." | Look up the exact `<script-slug>` in `references/commit-scopes.md`; `workflow.py` relies on exact scope matching. |

**Done when:** Changes are committed with valid scopes on `dev` or a topic branch, or for a release, `python tools/workflow.py check --json` and `--dry-run` succeed and `python tools/workflow.py release --non-interactive --push` (with `--files ...` for non-script files) exits cleanly.
